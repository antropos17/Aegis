## Proposed local caller contract

The future supervisor is a narrowly provisioned host authority with protected executable/configuration/inventory. It launches one pinned trusted broker instance, retains its process/token handles and birth identity, and registers that instance for one operator/session. An ordinary renderer sends requests to this broker; it cannot nominate a trusted broker PID, token, owner, image, root or VM. Separate trusted broker identity and guest-inaccessible process/handle permissions require later provisioning and native tests.
Use one local-only named-pipe protocol between broker and supervisor, with a protected endpoint DACL, remote-client rejection and first-instance ownership. Authenticate both directions: the broker verifies the actual server against the supervisor's protected installation/held-instance registration; a pipe name or random suffix alone is insufficient. This is proposed future configuration, not permission to change ACLs or install a service now.
For each complete bounded message, call `ImpersonateNamedPipeClient` on its connection, open/query the resulting thread token, and require the registered principal, logon authentication LUID, Windows session, permitted token type/impersonation level and expected integrity/restriction policy. Reject anonymous/failed queries. The token reflects the last read message: serialize read/authentication and never authenticate one frame then authorize later unexamined frames.
Query the OS client process identity from that pipe connection, then compare it with the supervisor's already-held broker process handle, queried birth time and still-alive state. Query the held process token and require agreement with the accepted caller context. Client-supplied PIDs and same-SID matches never establish registration. Do not reopen a process solely by a received PID; expiry/exit revokes the held instance.
Always revert impersonation before acting as supervisor. Impersonation failure dispatches nothing; revert failure terminates the worker handling the connection and revokes that channel rather than continuing under an uncertain token. No privileged effect occurs while parsing/authenticating untrusted bytes.
The supervisor derives a short-lived in-memory `CallerContext` from these observations: registration generation, held broker reference, principal/logon/session binding, operator mapping and allowed session IDs. It is never deserialized from the wire. Same-user injection, duplicated pipe handles or compromised trusted broker remain separate attack surfaces; protecting broker process access is a required native gate, not solved by a PID/birth comparison.
After supervisor restart, old handles and connection admissions are gone. A newly authenticated broker must obtain a new registration generation; it cannot resume an old admission by replaying saved identifiers. Recovery may inspect/stop only resources independently proven owned.

## Protected inventory and pre-mutation fence

Provision a supervisor-owned inventory directory on one explicitly authorized local volume. Only the supervisor authority and installer/administrator recovery role may change it; the UI, broker, guest and agent may not write it. Protect all ancestors and executable/configuration dependencies. Administrator/kernel compromise is outside this proposed boundary and must remain stated.
An ownership record is created by the trusted provisioner/supervisor, never inferred from a journal or imported from guest JSON. Store schema/revision; protected installation/host binding; authorized owner principal and operator/logon policy; exact volume plus root `FileIdInfo` 128-bit identity; owned resource identities; exact VM ID and fresh epoch; selected image file identity/hash/size/provenance; runtime/bootstrap manifest; endpoint service registration identity; approved realized configuration; and permitted lifecycle operations.
Names, drive letters, volume serials or GUIDs alone are insufficient. Reopen roots/images no-follow through pinned ancestors, query full file identities and volume/device binding, reject ADS/reparse/shared paths, verify protected ownership/ACLs, and compare all expected identities. Hold relevant handles while operating. Volume serial and file ID are corroborating local observations, not cryptographic host identity; restored/cloned storage needs new reviewed registration.
Immediately before every mutation, under one per-resource supervisor lock: authenticate current caller; validate active registration and revocation generation; load the protected record; match host/owner/root/image/VM/epoch; independently query the exact management-provider VM object and realized disks/devices/configuration; require the expected phase and no earlier unresolved management jobs; persist and flush the operation intent; recheck the revocation generation; dispatch only the fixed operation for that held inventory record.
Do not resolve a fresh target by a supplied name/path after the fence. Bind asynchronous management job handles/identifiers to this operation and track them to actual settlement. A timeout is pending/unknown, not cancellation. Reuse the synthetic revision-fence ordering only after native management observations implement it.
Protected inventory publication uses create-new owned staging, complete write/flush, atomic no-overwrite or compare-generation replacement under the lock, and independently checked identity. Journal intent precedes effect; inventory/receipt failure prevents new launch/admission. Crash between intent, dispatch and completion leaves an explicit pending operation for reconciliation, never an inferred success or automatic start retry.
Keep durable sequence/revocation high-water state with the protected record. A checksum/HMAC over user-writable state supplies no rollback authority; keys, labels and journal chain links do not grant ownership. Whole-host backup rollback detection and power-loss durability of directory publication remain unqualified without a separate durable-anchor/recovery design.

## Operations, replay and revocation

Use an exact-schema versioned frame, maximum 4096 bytes, with fixed operation enum, supervisor-issued opaque session reference, current registration/epoch, per-connection sequence and unique operation ID. No commands, PowerShell, raw host paths, arbitrary VM selectors, registry entries, image mounts or credentials. Reject unknown/duplicate fields, versions, extra frames, invalid encoding, expired context, out-of-order sequence and forbidden phase.
Initial future allowlist: `inspect-owned`, `prepare-owned`, `release-fixed-fixture`, `stop-owned`, `query-operation`, `revoke-session`. `prepare-owned` selects only a pre-registered disposable resource; it cannot create arbitrary resources. Provisioning and deletion are separate operator/installer workflows. Sealed import remains a separately reviewed byte artifact; host export is absent.
Bind each accepted operation to caller registration, owner/session, protected record revision, VM/epoch, policy revision and exact argument digest. Persist a unique mutation ID before dispatch. An identical retry returns the recorded state; changed arguments or context with a reused ID fail. Unknown outcomes are queried/reconciled and never redispatched as a new launch.
Caller exit/disconnect, registration loss, explicit revoke, token/peer change, epoch change, expired lease, journal failure or failed observation immediately denies new admission/release and invalidates outstanding channel capability. Dispatch and revoke share the supervisor lock; already-dispatched work remains tracked. Supervisor-owned emergency stop may continue after caller loss, but still requires proven resource ownership. Cleanup failure retains resources and state `cleanup-unknown`.

## Guest peer admission

Future native Hyper-V sockets must bind the exact owned VM and approved nonzero service, rejecting special/wildcard/foreign VM routes. Read the connected peer from the actual accepted socket and match it to inventory plus independently observed management state; transport support for those observations must be tested before reliance. Address serialization cannot supply this evidence.
VM peer identity identifies a machine, not the guest process. Before project code exists, a trusted guest bootstrap/observer must bind its held process, token, Job and pinned runtime/image to a fresh host challenge and epoch. Deliver a one-session capability through a separately reviewed protected bootstrap channel; no argument/env/log/guest-agent-readable key placement. Its concrete protected delivery and guest runtime provenance remain unimplemented blockers.
Require all three independently: authenticated host caller/owned inventory, actual exact VM peer, and admitted bootstrap instance/epoch. HMAC then binds possession and frame order to that established context. A guest result or `stopped` frame cannot attest host ownership, VM off state or complete process closure. Stop requires actual management-job settlement, exact VM-off observation and independently observed guest lifetime closure; otherwise deny export/credentials and retain uncertainty.

## Native acceptance tests required before implementation acceptance

| Test family | Harmless independent oracle and required result |
| --- | --- |
| Caller positive/negative | Authorized held broker succeeds; same-SID sibling, different user/logon/session, low-integrity/anonymous/remote caller, forged PID/session and unregistered instance produce no mutation sentinel. |
| Pipe/server and process races | Squatted server, PID reuse, exited/replaced broker, duplicated pipe handle, caller thread impersonation changes, partial frame and impersonation/revert failure never acquire authority; record actual OS token/process observations. |
| Broker/inventory protection | Agent/UI/broker attempt executable, ancestor, pipe/inventory ACL and inventory writes; unauthorized effects fail. A trusted disposable positive control proves the target is writable when intentionally allowed. |
| Ownership substitutions | Wrong host/owner/VM/epoch, root/volume replacement, junction/hardlink/ADS, drive remap, swapped image/disk/parent chain and altered realized devices block before effects; unrelated VM/file canaries remain unchanged. |
| Replay/revocation | Duplicate/reordered/version-confused frames, changed-argument ID reuse, foreign sessions, reconnect/restart replay, simultaneous revoke/dispatch and expiry cannot cause a second or post-revocation admission. |
| Journaling/crash recovery | Disk-full, short write/flush error, torn/replaced/forged journal, corrupt inventory, crash at each intent/effect/commit boundary and late management completion yield pending/cleanup-unknown; no name-based cleanup or automatic resume. |
| Actual guest peer/bootstrap | Exact VM positive control; foreign/wildcard/service peer, cross-VM relay, wrong bootstrap/token/runtime, stolen synthetic MAC key, prior-epoch initialized frame and guest result spoofing all fail admission. Bootstrap key secrecy needs actual guest access tests. |
| Lifetime/stop | Broker/supervisor/guest death, boot restart and asynchronous start/stop races retain tracked jobs and require fresh exact VM-off plus guest Job-empty evidence. A signed or HMAC-valid stopped frame alone cannot pass. |
| Resource preservation | Fail each setup/cleanup step; only independently identified owned objects may change. Preserve other VMs, services, roots, host settings and receipts; verify bounded logs, storage growth and cleanup uncertainty. |

No native tests above ran for this design note. Future implementation needs actual Windows evidence, the ten repository checks, and a scoped independent boundary review; this document grants no acceptance or provisioning authority.
