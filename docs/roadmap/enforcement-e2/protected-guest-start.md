# Administrative protected guest run

After a settled native transition, state admission requires agreement between the retained native VM identity and a fresh Hyper-V cmdlet observation. Cmdlet disagreement uses a five-second polling window in addition to provider-call time, without another provider request. Native state loss fails immediately. Startup failure evidence contains at most sixteen VM-scoped event IDs and finite hexadecimal codes from named error fields; event messages, XML, paths and account values are excluded. The native corpus also probes bounded firmware start/stop on inert media; this does not qualify persistent OS boot or agent execution.

VMMS adds the Windows `vmWorkerProcess` capability to runtime configuration files. The tree validator derives that one capability through [DeriveCapabilitySidsFromName](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-derivecapabilitysidsfromname) and permits it only on the original VM GUID's `.vmcx`, `.vmgs` and `.vmrs` leaves under its private Machine subtree, with a finite file-access mask. Directories, media, other VM GUIDs and arbitrary capabilities remain refused. This capability is the AppContainer portion of Windows' [dual-principal access check](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer): the normal user/group side still requires SYSTEM, Administrators or the original VM SID. High-integrity labels and original namespace/identity checks remain required. No existing ACL is broadened or repaired by this recognition.

`scripts/installation/protected-guest.ps1` extends the original, elevated `New-ProtectedInstallation` association. It is a repository administrative API, with its native sources present, and is not exposed through the ordinary caller or installed-owner dispatcher. Loading it grants no launch capability. The administrator supplies a trusted offline, bootable Windows VHDX and its exact byte count and full SHA256. The base guest must permit administrative PowerShell Direct and have no preexisting `C:\ProgramData\AEGIS` root. The image and administrative guest credentials remain trust inputs; hashing alone does not establish image safety.

Use `Set-ProtectedGuestDisk $association $diskRequest`, then `Start-ProtectedGuest $association`. The request is exactly `{path, bytes, sha256}`, with a canonical local path, an Int64 byte count from 1MiB through 64GiB and a lowercase 64-character digest. Hydration streams into the provisioner's original standalone disk under its original file ID, private DACL and High integrity label. It never attaches or adopts the source disk. Secure Boot, a new local TPM protector and disk-first boot are configured while Off. A successful hydration rotates the inspection-only registration through the existing protected upgrade transaction.

Start consumes one durable operation on that association, checks the exact VM identity and configuration, and uses the retained native VMMS lifecycle owner. Generation2, fixed4GiB memory, two processors, disabled checkpoints, no NICs, the original single disk and original ISO are required. During hydration the disk has a data handle allowing write but excluding deletion. During actual execution VMMS requires exclusive data access: the coordinator retains a metadata handle, original file ID, private High-integrity namespace and ordinary-caller mutation denials. It does not claim sharing-based delete exclusion for a running VHDX. Native unknown settlement retains the transaction; no name-based recovery, retry or cleanup is authorized.

`Invoke-ProtectedGuestAgent $association $guestAdmin $freshAgent $package $arguments $milliseconds` admits one bounded package through administrative PS Direct to the created VM ID. The package has the same three fields, with an Int64 size up to4MiB. The account name must be a fresh `AegisAg` plus12 lowercase hexadecimal characters; its password is supplied as a PSCredential and never enters an argument or environment block. The guest creates this ordinary Users-only account, enforces its512MiB NTFS quota on C:, creates private directories atomically, pins and hashes the executable, and starts it suspended on a private desktop. Its exact token SID, absence of administrator groups/elevation, session, image, birth and initial Job membership are checked before resume. The Job limits active processes to32 and both each process and the whole Job to512MiB; execution lasts100 through120000ms. A fixed environment excludes inherited administrative secrets. Success requires process exit, whole-Job closure and desktop closure. Nonzero agent exit is returned as an exit code and must be handled by the caller.

Always call `Stop-ProtectedGuest` after a known running operation, then uninstall through `Remove-ProtectedInstallation`. Confirmed native Off precedes restoring the offline data pin, checking the original disk ID, refreshing the storage binding and rotating registration. Unknown VMMS settlement prevents compensating state changes. A lost guest worker never authorizes another agent attempt; confirmed VM Off closes that guest execution boundary. The one-use guest's files and account remain in its disk until owned VM/image removal. This API provides no restart/recovery procedure for a retained unknown operation.

The base image and trusted administrators/VMMS are outside the ordinary-agent boundary. Guest quotas limit allocations charged to that new principal; they do not constrain writes performed by privileged guest services or preexisting files owned by another principal. Approved images must not expose such writable privileged files to ordinary Users. Host headroom is observed during the bounded agent call. There is no network, provider credential, GUI launch, production promotion or independent A1-A4 acceptance implied by these administrative controls. Keep `launchAllowed=false` until the separate acceptance process completes.

Hosted native qualification exercises actual Hyper-V provisioning and offline boot-disk hydration. An empty disk is not a persistent running-OS control: firmware can stop after an initial Running observation. The full Windows corpus confirms absence of its earlier VM, creates a private offline copy of that actual installed Windows disk on D:, removes the old C: assets, and exercises actual start/agent/stop through this administrative path on a fresh protected VM. Its standard agent verifies argument preservation, private namespace write denial, an enforced quota refusal, bounded working writes and descendant cleanup. The receipt retains the tested source and compiled payload bindings. Earlier failed observations remain failed.
