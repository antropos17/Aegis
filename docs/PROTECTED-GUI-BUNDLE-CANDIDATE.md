# Protected GUI bundle candidate intake

The optional installer GUI input captures a complete, explicitly selected unpacked Electron package and the installing process's observed elevated/linked token relation. It stages a protected candidate beneath the original installation stage. It does not launch a GUI, enroll an Electron process, enable a renderer route, approve provider/bootstrap state, or change `launchAllowed`.

## Complete bounded package

`node scripts/produce-protected-gui-manifest.mjs <source-directory> <new-manifest-file>` produces canonical integrity metadata. The caller must select the package explicitly. The manifest is an integrity description, with no signature or release approval implied. Both `AEGIS - AI Monitoring & Threat Detection.exe` and `resources/app.asar` must exist. Every other file and directory, including unpacked resources, must be listed.

The closed grammar permits at most 1,024 files, 1,024 directories, 512 MiB per file, 2 GiB total file content, 512 KiB of manifest, 240 characters per relative path, and depth 12. Unknown members, case aliases, traversal, Windows device names, trailing dots/spaces, named streams, hardlinks and reparse points cause refusal. These are bounded intake limits; compatibility with a particular current packaged build requires measuring that build.

`ProtectedGuiBundleFiles.Capture` holds original source handles and verifies the complete tree and hashes. `Stage` streams through bounded buffers into fixed nested `GuiBundle`, retaining each file's original CreateNew handle before writing. Created directories are retained before child creation. The supplied protected descriptor must keep write authority with SYSTEM/Administrators. The GUI principal and dedicated operator receive read/execute access only.

The staged owner is independent of the external capture. Closing the external capture after successful staging does not lose staged ownership. Upgrade copies the previous retained staged bundle into a new original stage; it does not recapture external paths or select another principal. The prior bundle remains intact until commit. Rollback removes only the new original objects.

`Stage(originalRoot, descriptor, originalParent, originalPrincipal)` retains the exact original parent/principal association. `RenameStage(originalRoot, originalParent, destination)` is one serialized transition: it checks protected root/parent and complete bundle, releases descendant handles, renames the original root, and reacquires each original 128-bit file ID through `OpenFileById` using an independently verified same-volume parent hint. The original root/parent handles and immutable per-entry creation IDs, security, metadata and manifest remain retained throughout. Every resumed entry must match its original ID/security/type/streams/metadata/hash and exact new path, and the complete tree and original principal must pass before reuse. Unsupported reacquisition or any failure after release makes uncertainty sticky. There is no public begin/end gap, pathname adoption or automatic cleanup after an uncertain transition.

Disposable native controls on the development host showed an empty original stage can rename, while retained descendant directory handles and even file READ_ATTRIBUTES-only handles cause Win32 access denied. A separate original-ID reacquisition control succeeded. These observations motivate the explicit protected transition; they do not qualify all Windows/filesystem combinations. The transition relies on the protected namespace rather than continuous descendant-handle or data-write exclusion. External source pins remain strict.

Cleanup first verifies the exact retained set and retires it in reverse creation order. Original creation handles receive disposition directly. On this development host, disposition through the resumed by-ID file handle returned Win32 87, after successful rename/identity/hash checks. Resumed originals therefore retain that by-ID pin while opening their already recorded expected namespace link with OPEN_EXISTING and OPEN_REPARSE_POINT. That temporary candidate must match the immutable original volume/128-bit ID, exact name, descriptor, type, streams, single-file-link count, metadata and hash before disposition. Root/parent are checked again. Directory metadata is compared against the retained original's current observation after the known child retirements; the immutable creation journal is not refreshed. An unmatched candidate is closed without mutation. This link cannot recover missing identity, substitute for unsupported ID reacquisition, or establish ownership of a replacement.

Unknown children, substitutions or failed cleanup preserve uncertainty and retained ownership for the outer transaction. Disposing an owner closes handles without claiming successful removal. The observed Win32 87 is evidence from this host rather than a claim about every Windows/filesystem implementation.

## Installing principal observation

`ProtectedGuiIdentity.CaptureInstaller` observes the current non-impersonating process token, requiring an elevated primary token in an interactive session and its same-SID/session linked limited medium token. A reciprocal link must identify the original elevated token. SID, session, token IDs, authentication IDs and security roles are observed independently; the two authentication IDs need not be equal.

Currentness retains the original token objects and checks the process token and linked relation again. ModifiedId must remain stable during each observation, while legitimate installer privilege adjustments may change it between observations. This binds principal/token identity, without asserting an immutable privilege or group-enable snapshot. The candidate derives no runtime authority from privilege changes.

Alternate-credential UAC identifies the elevating administrator and that administrator's linked token. It does not prove the identity of the desktop user who initiated the prompt. No ActiveConsoleUser lookup or supplied SID is substituted for native observation. Session 0, unsupported linked tokens, mismatched SID/session/security role, impersonation and token replacement are refused.

## Candidate record and verification limits

`New-ProtectedGuiStage` consumes only the existing stage producer's policy bytes and binds the candidate to their digest, installation/selection/revision/epoch tuple, bundle generation, original bundle ID and complete manifest digest/counts. The fixed record is `registered-gui-candidate.json`, with `status: "candidate"` and `guiEnrollment: false`. The original principal remains associated with staged owners through upgrade and cleanup.

`New-ProtectedInstallation` accepts optional final `-GuiBundle @{ sourceRoot = <string>; manifest = <byte[]> }`. Those are the only allowed keys; the manifest must contain 1–524,288 bytes. Null preserves installation without a GUI candidate. Initial capture precedes account/VM effects. Its external source capture closes after staging; the original principal remains in the installation context. Update accepts no replacement GUI input and borrows the previous staged bundle/principal. A marked failure retains `Context.failedStage`; cleanup uncertainty prevents retirement of those originals.

Dedicated fixtures exercise native filesystem retention, streams, hashes, complete membership, copy, rename, partial rollback and refusal before deleting foreign content. Test builds can model descriptor authority and the elevated/linked principal pair; those factories are excluded from the production compilation. Modeled controls do not qualify real administrator ACLs, actual UAC elevation, GUI execution, native inspection enrollment, live transport, or end-to-end enforcement. Production compilation and independent review remain required alongside focused behavior tests.
